Things to write in the README rather than pretend to solve.

1. THE MODEL CANNOT SEPARATE DATA FROM INSTRUCTIONS, AND NO WORDING IN THIS HARNESS WILL MAKE IT. This is the whole problem and it lives in the weights, not the loop. My sanitised run is the honest illustration: control-token forgery went to 0/6, but the same page's plain prose still redirected the model into file tools 3/3. Mitigations 1-6 remove the deterministic hijacks and raise the cost of the probabilistic ones; the residual is not zero and does not go to zero. The literature that does eliminate it on AgentDojo (CaMeL and successors) does so with capability propagation and a deterministic policy engine outside the model — a quarantined LLM that never sees a tool handle, plus dataflow labels on every value. That is a different architecture, not a few hundred lines bolted onto run_agent, and CaMeL still pays utility for it (77% vs 84% undefended).

2. FILTERS AND DETECTORS LOSE TO ADAPTIVE ATTACKERS. A keyword list for "ignore previous instructions" is theatre — the adaptive-evaluation work through 2026 keeps showing that defences measured against fixed attack suites collapse when the attack is optimised against the defence. Ship mitigation 1 because it closes a mechanism, not because it recognises a phrase. Do not add a "suspicious content" classifier.

3. run_python AND run_bash ARE NOT SANDBOXES, AND CANNOT BE MADE INTO ONE HERE. tools.py already says this in two docstrings, and it is the honest position: `subprocess.run([sys.executable, "-I", ...], cwd=workspace)` isolates the interpreter, not the process. The code runs as the invoking user with full filesystem and network access; _resolve_inside (tools.py:252) confines the file tools but does nothing to a child process; BASH_REFUSED (tools.py:28) is a regex list that the file itself correctly describes as not a security boundary. Real confinement is a container, a seccomp profile, or a separate user — an OS-level decision, not a Python one. Until then the blast radius of a successful injection is the user account, and mitigation 3 (never let a web-tainted turn reach these tools) is the only thing standing in front of it.

4. EXFILTRATION VIA THE SEARCH QUERY IS UNFIXABLE WHILE THE MODEL WRITES THE QUERY. Any string the model can put in a query reaches a third party. Caps on query length reduce bandwidth; they do not close the channel.

5. TAINT DOES NOT EXPIRE. A poisoned observation stays in `messages` for the rest of the session, so a turn-scoped gate leaks across turns in an interactive session. Either taint the session once a web tool has run, or drop the observation from history after the turn — and accept that dropping it loses follow-up questions about what was found.

6. PROVENANCE IS OUT OF SCOPE. The harness cannot tell a real page from one built to rank for the query the model just wrote, or notice that a page changed between the model reading it and a human checking it.

7. THE ANSWER IS NOT VERIFIABLE. Even with everything above, the user is reading a 350M model's summary of attacker-controlled text. Content-level lies — a wrong price, a wrong version number, a wrong command to run — pass through untouched, and the harness should not imply otherwise in its output.
